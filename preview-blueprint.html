An interactive tutorial

Make an AI coding agent actually reliable.

Your model is not the problem. The environment you run it in is. This tutorial walks through harness engineering — the discipline of designing instructions, state, verification and feedback around an agent — and lets you feel each failure mode with a simulator instead of just reading about it.

What you will be able to do

By the end you should be able to look at a failing agent session and name the layer that failed — instructions, tools, environment, state or feedback — instead of blaming the model. That single diagnostic habit is most of the skill. Everything else in this tutorial is the machinery for each layer.

Chapter 0 of 10

Chapter 01 · Diagnosis

Strong models don't mean reliable execution.

Claude Sonnet 4.5 scored 77.2% on SWE-bench Verified in September 2025. Then you hand the same model your actual repo — vague ticket, no tests, conventions that live in a Slack thread — and it confidently ships something broken.

That gap has a name: the capability gap. Benchmarks hand the agent a clean issue description, an existing test suite and a working environment. Real work asks it to invent all three. The model didn't get worse between the benchmark and your repo; the harness did.

The cleanest evidence comes from Anthropic, who ran the same prompt — "build a 2D retro game editor" — on the same model (Opus 4.5) under two different harnesses:

RunHarnessTimeCostOutcome
BareSingle prompt, no planner, no evaluator20 min$9App opened; entities ignored input
HarnessedPlanner / generator / evaluator split6 h$200Core loop playable; unfinished edges

Same weights. Different tack. OpenAI's harness engineering write-up is blunter still: in a well-harnessed repository Codex goes from unreliable to reliable — not "a bit better", but a qualitative jump.

The five ways sessions actually fail

Almost every bad agent session is one of these. Learn to recognise them and you have a triage list, not a mystery.

  • Vague requirements. "Add a search feature" — search what, ranked how, paginated? The agent guesses. A wrong guess costs several times more than the sentence that would have prevented it.
  • Unwritten conventions. Your team is on SQLAlchemy 2.0; every endpoint must pass OAuth 2.0. The agent has never seen that rule, so it cannot comply.
  • Broken environment. Missing dependencies and version conflicts burn context on pip install errors instead of the task.
  • No verification. Nothing executable says what "done" means, so the agent uses its own standard: "the code looks fine." Anthropic also observed context anxiety — as the window fills, agents rush, skip verification and pick the easy solution.
  • Cross-session amnesia. Every new session re-explores the repo and re-litigates decisions. Failure rates spike sharply on tasks longer than about 30 minutes.
Principle

When something fails, don't swap the model first — check the harness. If the same model succeeds on a similar, well-structured task, the weights are fine and the environment is not.

Lab 01 · Failure triage not started

Pick the symptom you have actually seen. Each one maps to a specific harness layer and a specific fix — that mapping is the whole diagnostic method.

The habit to build

Attribute every failure to a layer before you change anything: was the task unclear, was context missing, was the environment broken, was there no verification, or was state lost? Anthropic's own diagnostic loop is exactly this — execute, observe the failure, attribute it to a layer, fix that layer, re-execute. You will find "the model isn't good enough" appearing in your notes less and less.

Chapter 1 of 10

Chapter 02 · Definition

A prompt file is not a harness.

People say "harness" and mean "the system prompt I wrote." That is one of five subsystems. The other four are where most reliability actually comes from.

The analogy that makes it click: a new engineer joins your project with no README, no comments, nobody to ask, and CI config buried somewhere. Smart people still struggle — they spend their day working out what the project is instead of solving the problem. An agent has it worse: it can only see the files you put in front of it and the commands it can run.

The five subsystems

SubsystemWhat it carriesTypical artefacts
InstructionsRules, conventions, definition of doneAGENTS.md, CLAUDE.md, docs/
ToolsWhat the agent can actually doshell, test runner, linters, MCP servers, scripts
EnvironmentA runnable, isolated place to workinit.sh, lockfiles, containers, git worktrees
StateWhat is done, why, and what is nextfeature_list.json, progress log, git history
FeedbackEvidence of what actually happenedtests, type checks, e2e runs, traces, logs

Three habits separate a real harness from a prompt dump. Give a map, not a manual — AGENTS.md is a directory page around 100 lines long, not an encyclopaedia. Constrain, don't micromanage — enforce invariants and let the agent choose the implementation. And remove one at a time and watch — delete a subsystem, see how much performance drops, and you learn which parts are actually load-bearing today.

Two anchors

OpenAI frames the core principle as "the repo is the spec." Anthropic frames it as state persistence and explicit recovery paths. Different words, same claim: everything outside the model weights decides how much of the model's capability gets realised.

Why the weakest link wins

A harness is a chain. A brilliant instruction file cannot rescue an agent that cannot run the tests; a perfect test suite does nothing if the agent never learns what state it is in. That is why the scorecard reports the minimum rather than the mean: your session quality is set by whichever subsystem you have neglected, and adding strength anywhere else is mostly wasted effort until you fix it.

Chapter 2 of 10

Chapter 03 · Instructions

If it isn't in the repo, it doesn't exist.

An agent has three inputs: the task description, the contents of the repository, and the output of commands it runs. Slack, Jira, Confluence and the architecture decision you made on Friday are all invisible to it.

This is not a "write more documentation" problem. It is a "put the decision where it will be needed" problem. A 50-line ARCHITECTURE.md inside src/api/ beats a 500-page Confluence space nobody maintains, because information only helps at the moment it is in front of the reader. Proximity beats length.

The fresh-session test

You can measure whether your map is good enough in one move: open a brand-new session, give it nothing but the repository, and see whether it can answer five questions without asking you anything.

QuestionWhere the answer must live
What is this system?README.md / AGENTS.md
How is it organised?ARCHITECTURE.md, module docs
How do I run it?init.sh, Makefile, package scripts
How do I verify it?test / lint / typecheck commands
Where are we now?feature_list.json, progress log, git log

Chapter 3 of 10

Chapter 04 · Instructions

Your 600-line instruction file is hurting the agent.

It started at 40 lines. Every mistake added a rule. Three months later a simple bug fix means reading deployment notes, six style opinions and a lesson from a WebSocket leak — and the security rule on line 300 gets ignored.

Four things go wrong at once. Context budget disappears: a 600-line file can eat 10–20k tokens, 8–15% of a 128k window, before the agent reads a single source file. Position matters: Liu et al. (2023) showed models use information in the middle of a long context far less reliably than information at the start or end. Priority flattens: "never use eval()", "prefer functional style" and "watch for that leak" all look identical in a list. And files only grow, because deleting a rule feels riskier than adding one.

The fix is architectural: a short entry file that routes, plus detail that is revealed on demand. 50–200 lines at the root; everything else behind a link the agent follows only when the task needs it.

The rule of thumb

Keep the entry file under about 200 lines and hold it to hard constraints, a startup workflow, and the definition of done. Push everything else — API conventions, database rules, deployment notes — into topic files the agent opens only when the task calls for them. Then audit quarterly and delete what no longer earns its place.

Chapter 4 of 10

Chapter 05 · State

Sessions end. Understanding doesn't have to.

The agent runs 30 minutes, gets most of a feature done, and runs out of context. The next session remembers none of it: not the decisions, not which files changed, not what the tests said.

Bigger windows do not fix this. The information an agent produces is not uniformly valuable: intermediate reasoning carries the why — why option A beat option B, why that library, why this shortcut — and the final output only carries the what. Compaction keeps the code and drops the reasoning, so the next session sees the artefact and "optimises" away a decision that was deliberate.

Worse, agents know when the window is filling. Anthropic describes context anxiety: as the budget tightens, the agent rushes the finish, skips verification and takes the simple path. A harness that never leaves a written handoff guarantees that every session is somebody's first day.

What a handoff actually contains

ArtefactAnswers
feature_list.jsonWhat is done, what is active, what is blocked — with the command that proves it
progress.mdWhat happened last session, what is verified, what is next
Decision notesWhy this approach and not the obvious one
Git checkpointThe exact repository state to start from
init.shThe one command that makes the environment trustworthy again

Initialisation deserves its own phase, not a corner of the feature work. Implementation maximises verified features; initialisation maximises the reliability of everything that follows. Mixed together, the agent does what is visible — it writes code — and skips what is invisible — verifying that the test framework works. The cost lands in session two, when nobody can run anything.

Chapter 5 of 10

Chapter 06 · Scope

One feature at a time, or nothing finishes.

Ask for "user authentication" and you get a schema change, routes, a mail service, bcrypt, a refactored error middleware and a reorganised test directory. Twelve files, 800 lines, nothing working end to end.

This is arithmetic, not personality. Give the agent context capacity $$C$$ and let it activate $$k$$ tasks at once: each task gets $$C/k$$. Once $$C/k$$ drops below what a single task needs to be reasoned about and verified, none of them finish. The agent did not get dumber — you divided its attention.

WIP = 1

Pick exactly one item, implement it, run end-to-end verification, commit, update the list, unlock the next. Anthropic's long-running-agent guidance is explicit: one feature at a time, verified and recorded before moving on.

Chapter 07 · Feedback

    
“Done” is a claim. Evidence is a fact.

    
Modern neural networks are systematically overconfident — reported confidence runs above actual accuracy, as Guo et al. showed in 2017. An agent that feels finished is reporting a feeling.


    
Unit tests have a designed blind spot: they isolate. Mock the dependency, test the unit, and every module passes while the system is broken. Four classes of defect survive a green unit suite:


    
    
      
  • Interface mismatch — the renderer passes a relative path, the preload script expects absolute. Both sides mock, both pass.
    • 
      
  • State propagation — a migration changes the schema; an ORM cache still holds old-shaped entries.
    • 
      
  • Resource lifecycle — file handles and connections acquired across components, released by none.
    • 
      
  • Environment dependency — correct against mocks, wrong against real config, latency or an unavailable service.
    • 
    


    
End-to-end verification does something subtler than catching bugs: it changes how the agent writes code. When the agent knows a full flow will be executed, it starts asking how its interface connects upstream, respects architectural boundaries, and handles error paths. The test is not only a filter, it is a constraint on the shape of the solution.

      The pattern
      
Lint passes. Twelve unit tests pass. The feature is still broken in three ways that only appear when the flow runs. If your definition of done stops at "tests are green", you have automated the exact gap the agent is worst at.

    


    
The fix is structural: separate the agent that does the work from the agent that checks it. Anthropic's finding is that agents praise their own output; a checker with its own rubric and its own evidence requirement does not. Then require the evidence to be recorded — not summarised as "looks good", but as the command that ran and the output it produced.

Chapter 08 · Feedback

    
If you can't see it run, you're guessing.

    
Code review shows what was written. Traces show what actually ran. Without the second, every retry is a random walk and every evaluation is a matter of taste.


    
Four costs arrive together when a harness has no observability. You cannot distinguish correct from looks correct. Evaluation becomes mysticism, because two evaluators with implicit standards disagree and neither can say why. Retries become blind, so the agent "fixes" unrelated code while the real cause sits untouched. And the handoff cliff gets steeper, because the next session must diagnose the system from scratch.


    

      

        
Without observabilityWith a contract and traces

        
          
Planner"Make the app dark mode"Sprint contract: components, per-component criteria, exclusions

          
Evaluator"Doesn't feel right""Button contrast 2.1:1, WCAG AA needs 4.5:1"

          
Retries3–4 blind attempts, ~45 minOne targeted fix, ~15 min

        
      

    


    
Then there is the end of the session. Lehman's laws say a changing system grows more complex unless you actively manage it, and agents accelerate that: OpenAI observed Codex copying whatever patterns already exist in the repo, good or bad. Left alone, drift compounds. Their team initially reserved Fridays — about 20% of weekly capacity — for cleaning up "AI slop", then replaced it with encoded golden rules, periodic cleanup tasks and rules promoted from documentation into tooling.


    
What "clean state" actually means

    
    
      
  • The build passes, and the next session does not have to fix it first.
    • 
      
  • All tests pass, including the ones that existed before this session.
    • 
      
  • Verification ran in CI, not just on the author's machine.
    • 
      
  • Feature state and progress are updated with evidence.
    • 
      
  • Temporary files, debug prints and scaffolding are removed.
    • 
      
  • The standard startup path still works from a cold clone.
    •

Chapter 09 · Automation

    
Stop prompting. Start specifying a stopping condition.

    
Everything so far assumed you were at the keyboard, typing. Loop engineering is the move from "do this next" to "keep going until this is true" — and the difference is one line.


    
In early 2026 Claude Code and Codex independently shipped /goal. You type a terminal state, close the laptop, and the agent analyses, codes, tests, fixes and retries until the condition holds. A loop has exactly three parts: a goal, a way to verify it, and a stopping condition. Without the third you have an agent that either quits early or never quits.

Step through four stages. Each one adds a capability that a single loop cannot express — and a cost you have to be willing to pay.

        

          
          
          
          
        

        

        

      

    


    
The four layers are a stack, not a sequence

    

      

        
LayerShapesAnswers

        
          
Prompt engineeringthe instructionWhat do we tell the model?

          
Context engineeringthe informationWhat should it know before deciding?

          
Loop engineeringthe runtimeHow does it iterate until the goal holds?

          
Graph engineeringthe systemHow do agents, loops and evaluators compose?

        
      

    


    
Each layer keeps the one below it. Every node in a graph still carries its own prompt, its own context, its own loop. What the graph adds is routing between them — and a bill. This term arrived in July 2026 through a joke between two engineers that the timeline took seriously; the fact-checking shows the "precursor" article predates the joke by two weeks, and the widely quoted "+18% accuracy, −85% cost" numbers come from an unrelated paper on chemical piping diagrams. The idea is real; most of the numbers around it are not.


    

      Decision rule
      
Once an agent needs specialisation, parallelism, shared state, verification and recovery at the same time, it has stopped being a loop. Until then, the loop is cheaper — and the orchestration tax is real.
